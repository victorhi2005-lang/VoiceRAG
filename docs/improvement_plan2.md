# VoiceRAG 強化計畫書2

## 一、計畫目標

VoiceRAG 目前已具備完整核心流程：音檔上傳、Whisper 語音轉文字、AI 摘要、文字切分、向量化、ChromaDB 儲存、多筆記本管理與 RAG 問答。

下一階段優先補強「可驗證、可追溯、可維護、可展示」四個面向。也就是說，不只是讓系統能回答，而是讓使用者能看出答案從哪裡來、品質是否穩定、系統架構是否能繼續擴充。

## 三、P1：建立 RAG 評估機制

### 目標

證明 VoiceRAG 不是只「看起來會回答」，而是真的能從錄音知識庫中找出正確資訊。

### 實作內容

1. 建立 10 到 30 題測試問題。
2. 每題記錄標準答案、應命中的來源音檔、應命中的知識片段。
3. 測試 Dense 檢索、BM25、RRF、Reranker 前後的差異。
4. 記錄回答是否正確、是否引用正確來源、是否產生幻覺。

### 預期成果

- 一份 RAG 測試題庫。
- 一份簡單評估報告。
- 可在畢業專題展示中說明系統正確率與改進效果。

## 四、P2：強化來源引用與時間戳

### 目標

讓 AI 回答可以被驗證，而不是只提供一段看似合理的答案。

### 實作內容

1. Whisper 轉文字時保留每段語音的 `start_time` 與 `end_time`。
2. ChromaDB metadata 儲存來源檔名、chunk 編號、開始時間、結束時間。
3. RAG 回答時顯示引用來源，例如：

```text
來源：example.mp3，02:13 - 02:48
```

4. 前端顯示「引用片段」，讓使用者看到 AI 是根據哪段內容回答。

### 預期成果

- AI 回答更可信。
- Demo 時可以清楚展示「答案來自哪一段錄音」。
- 更符合知識庫系統的「可追溯」特性。

## 五、P3：支援逐字稿查看、修正與重新索引

### 目標

解決語音辨識錯字會影響知識庫品質的問題。

### 實作內容

1. 上傳音檔後保存完整逐字稿。
2. 前端新增逐字稿查看區。
3. 讓使用者可以手動修正逐字稿。
4. 修正後重新切分、重新 embedding、重新寫入 ChromaDB。

### 預期成果

- 使用者可以修正 Whisper 錯誤。
- 知識庫品質可以持續改善。
- 系統更接近真實可用的知識管理工具。

## 六、P4：改善上傳處理進度

### 目標

讓使用者知道系統正在做什麼，避免長音檔處理時誤以為系統當機。

### 實作內容

1. 前端顯示處理階段：
   - 上傳中
   - 語音辨識中
   - 文字切分中
   - 向量化中
   - AI 摘要中
   - 完成
2. 後端先以簡單狀態訊息實作。
3. 後續可再升級為背景任務與任務進度查詢。

### 預期成果

- 使用體驗更好。
- Demo 流程更清楚。
- 使用者較能理解本地端 AI 處理需要時間。

## 七、P5：拆分 `backend/main.py`

### 目標

降低維護難度，讓程式架構更像正式專案。

### 實作內容

建議將目前集中在 `main.py` 的功能拆成以下模組：

| 模組 | 負責內容 |
|------|----------|
| `db.py` | SQLite 連線、資料表初始化、筆記本與對話紀錄操作 |
| `models.py` | Whisper、Embedding、Reranker 等模型載入 |
| `rag_service.py` | Dense 檢索、BM25、RRF、Reranker、Prompt 組裝 |
| `audio_service.py` | 音檔儲存、語音轉文字、文字切分 |
| `schemas.py` | Pydantic request / response model |
| `main.py` | FastAPI app 與 API 路由入口 |

### 預期成果

- 程式更好讀。
- 新增功能時不會全部塞進同一個檔案。
- 更容易除錯、測試與展示架構。

## 八、P6：強化前端 Markdown 與安全顯示

### 目標

讓 AI 回答格式更漂亮，同時避免直接使用 `innerHTML` 帶來的安全風險。

### 實作內容

1. 將 AI 回答中的 Markdown 正確渲染，例如粗體、清單、段落。
2. 避免直接把使用者輸入放進 `innerHTML`。
3. 對 HTML 做 escape，或使用安全的 Markdown renderer。
4. 保持回答內容可讀，但不要讓使用者輸入的 HTML 被瀏覽器執行。

### 預期成果

- AI 回答畫面更像正式知識助理。
- 降低 XSS 風險。
- 使用者輸入與 AI 回答的呈現更穩定。

## 九、P7：補齊資料管理與一致性檢查

### 目標

避免長期使用後，SQLite、ChromaDB、音檔資料之間出現不一致。

### 實作內容

1. 支援刪除單一來源。
2. 刪除來源時同步移除該來源對應的 ChromaDB chunks。
3. 建立資料一致性檢查：
   - SQLite 有來源，但 ChromaDB 沒有對應資料。
   - ChromaDB 有 collection，但 SQLite 沒有對應筆記本。
   - 音檔存在，但資料庫沒有紀錄。

### 預期成果

- 系統長期使用更穩定。
- 減少測試資料與孤兒 collection 累積。
